# Testing

Standalone FIFO tests require only Python's standard library:

```sh
python -m unittest discover -s tests -p 'test_queue.py' -v
```

Fifteen tests cover ordering, copied inputs, duplicate IDs, cancellation before/during generation, cancellation while waiting for Forge's lock, pause/resume, ownership, capacity, and shutdown. Regression cases cover releasing a pause after its last owner's job is cancelled or fails, preserving a pause while that owner still has work, retaining five clients' results, acknowledgement and stale acknowledgement handling, reserved delivery slots, and abandoned-result expiry.

Completion-boundary tests deterministically pause the worker at the first lock release that exposes a terminal job, without changing production job state. Polling must see the final result and freed inputs together for both normal completion and interruption. A second test fills 31 retained-client slots, completes the 32nd client, and verifies that a 33rd client is rejected at the same boundary. Before the atomic-completion fix, both tests failed (including both terminal-state subcases); after the fix, they passed.

Client protocol checks require Node.js 18 or later and only its standard library:

```sh
node --test tests/test_client.cjs
node --check javascript/generation_queue.js
```

Seventeen checks execute the real client script in a minimal simulated host. They cover HTTP-compatible IDs without `randomUUID`, denied storage, reconnect identity, native OFF behavior, three immediate startup submissions before any status reply, no poll-button click before Gradio load, and input preservation while only local settings are unavailable. Settings timeout does not replay expired clicks; known initial OFF uses native generation, while OFF with accepted work never starts native generation. Stale startup snapshots and an unconfirmed server-side OFF cannot stop result monitoring early. Other checks cover stalled status requests without overlapping requests or automatic resubmission, an early check, final acknowledgement after OFF, and native progress callbacks. The progress check preserves one monitor, validates and clamps progress, and rejects late updates after a job switch or completion. These checks do not exercise Gradio or a real browser DOM.

Development also used installed Gradio 4.40.0 and Forge's call_queue module with a fake CPU generator. Twenty-four Python checks passed (the 15 portable checks plus nine local integration/locale checks), including rejection of a direct startup submission while the server queue is paused. Earlier isolated Chrome integration covered sequential submissions, cancellation, reconnect, result delivery, failure/resume, and draining after OFF. Current DOM checks cover 11 locale values, button colors, a collapsed empty queue, and a constant 22px status area for 1 and 32 jobs, including opening the details overlay. CSS checks also verify a 2px row gap and a 100%-opaque dark popup background. The revised client was additionally checked in Chrome on an insecure HTTP test origin where `randomUUID` is unavailable: initialization and 20 distinct submission IDs succeeded. This uses a mocked page, not a connection to the user's Forge server.

Machine-specific integration harnesses and local artifacts are not included in this repository. Automated and isolated-browser checks are not real Forge/GPU acceptance tests. README Settings and expanded queue screenshots are user-supplied WebUI captures. The idle/generating pair is rendered from the current client script and stylesheet with sample job data and minimal host styles in an isolated browser. Neither the illustrative pair nor the user-provided capture substitutes for independent end-to-end GPU acceptance testing.

Later UI regression checks cover three active jobs displaying exactly three rows even when terminal history is present, counts including the running job, removal of completed rows, preserved error details and resume controls, distinct submission IDs, and a navy running row with soft white text and a blue left border. Waiting rows are not highlighted. Both pending-row cancellation and running-row interruption command dispatch were checked after the styling change. With the queue ON or OFF, completing or cancelling the last job removes the count and open details entirely (0px panel height); result acknowledgement remains intact, and new jobs reappear with details collapsed. Active queues retain the fixed 22px status area.

Progress-fill DOM checks render the real client and stylesheet at 25%, 65%, and 100%, checking the left-to-right widths in both the compact heading and running row, the row's accessible value and Japanese label, progress retained across a queue redraw, reset on the next job, ignored stale replies, and complete removal at idle. The heading remains closed while progress updates, retains its text node and 22px height, and still opens details when clicked. Paused queues retain Resume without a stale progress fill. Neither fill intercepts clicks or changes layout. Both share the fifth `onProgress` argument of Forge's existing `requestProgress` monitor; no new timer or endpoint is added. These checks simulate progress notifications and do not measure actual GPU progress accuracy.

A local isolated-browser check also loads Forge's actual `javascript/progressbar.js` with simulated `/internal/progress` responses. Updates at 25%, 65%, and 50% reach the extension's row, confirming the native callback connection. The captured 50% preview is illustrative; the user's Forge server and GPU are not used.

An installed-Gradio 4.40.0 browser fixture reproduces periodic infotext dimming by delaying queue-status responses by 180ms. Before the fix, the existing txt2img HTML reached 0.2 opacity while its contents stayed unchanged. After the scoped styling fix, it stayed at 1.0 during idle polling and while draining after OFF; a new CPU-generated result still replaced it correctly. With the queue OFF and idle, polling stopped and native generation retained its original 0.2 pending opacity. Isolated DOM checks also preserve the other tab's styling and the existing infotext DOM. This is a local CPU fixture, not a live Forge/GPU test.

No GPU is needed for the portable tests. For an actual Forge check, verify queue OFF behavior, multiple submissions, individual cancellation, completion, and the affected locale/theme, and report that separately from the automated results.

The current startup regression uses installed Gradio 4.40.0, Forge's native call_queue module, and a CPU-only generator. Hold the first status response for more than 11 seconds, submit three prompts, edit the prompt again, and switch the queue OFF before releasing that response. All three requests must be admitted before the first status reply, with three distinct jobs and the clicked inputs. Status requests must not overlap; the final CPU result and its acknowledgement must still arrive after OFF, followed by stopped idle polling. The adapter check also verifies one status handler with load/click triggers and the expected six outputs, with only the two original Generate/prompt events connected for admission. Isolated DOM checks verify Sending feedback, button colors, accepted-only counts, locales, cancellation, and layout. These checks do not measure actual Forge/GPU startup or generation speed.
